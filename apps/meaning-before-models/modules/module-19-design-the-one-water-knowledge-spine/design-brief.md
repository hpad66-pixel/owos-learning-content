# Module 19 Design Brief

## Module identity

- Course: Meaning Before Models
- Module: 19 of 19
- Title: Design the One Water Knowledge Spine
- Learning role: Capstone design and defense
- Estimated learning time: 75 to 105 minutes
- Design state: Ready for owner review
- Implementation state: Not started
- Final release state: Not approved

## Approved lesson contract

Central question: What is the smallest governed semantic pilot worth building?

Outcome: The learner can design, measure, and defend one bounded One Water Knowledge Spine pilot.

Required transfer: The learner can defend the pilot against challenges involving scope, evidence, architecture, value, security, and authority.

Misconception to overturn: A successful knowledge-graph pilot starts by building an enterprise graph.

Capstone work product: One Water Knowledge Spine Pilot Canvas and Decision Briefing.

## Capstone decision

The learner is not asked to draw the largest possible architecture. The learner must decide whether a ninety-day semantic pilot should be built at all:

1. Build the bounded pilot.
2. Revise the pilot before investment.
3. Do not build a knowledge-graph pilot for this question.

The lesson succeeds when the learner justifies the decision with evidence, controls, value, and explicit limits.

## Utility scenario

A fictional wastewater utility has difficulty assembling trustworthy context after wet-weather events. Asset, telemetry, inspection, work-order, incident, and procedure information is spread across systems and documents. Teams use different identifiers and terms.

The ninety-day pilot focuses on Lift Station LS-7, Overflow Event 21, the relevant upstream assets and evidence, and one human-approved draft inspection work order.

The bounded question is:

> When Overflow Event 21 occurs, which upstream assets and current evidence should a wastewater supervisor review before approving one draft inspection work order?

The pilot may resolve identities, traverse relationships, retrieve current evidence, validate required shapes, apply permitted inferences, assemble a decision package, request approval, create one draft work order after approval, verify the result, and record the audit.

It may not dispatch a crew, set priority, close work, change operations, publish an enterprise graph, issue credentials, bypass access controls, or approve production release.

## Opening experience

The learner sees an impressive enterprise graph proposal with thousands of entities and a promise to support every utility decision. It lacks one bounded question, baseline, decision owner, measurable target, authority boundary, and stop condition.

The learner must accept, revise, or reject it. The experience reveals that technical scale is not pilot readiness.

## Signature mechanism

### Knowledge Spine Pilot Review Board

The learner progressively assembles a connected pilot canvas and presents it to five reviewers:

- Wastewater operations
- Data and semantics
- Cybersecurity and access
- Governance and authority
- Finance and measurable value

Each reviewer tests a different failure mode. A persuasive answer without a source or control does not pass.

### Pilot Boundary Review

The learner reduces an unbounded enterprise proposal to one question, one decision, one action, one owner, one baseline, one ninety-day target, and explicit stop conditions.

### Graph Fit Test

The learner evaluates:

1. Are relationships central to the decision?
2. Must identities be reconciled?
3. Must meaning be shared?
4. Must evidence carry source, time, and authority?
5. Must rules or constraints be evaluated consistently?
6. Would a simpler table, report, search index, or workflow solve the problem adequately?

The sixth question can defeat the graph proposal.

## Visual Arsenal selection

| Visual | Class | Cognitive job | Required learner conclusion |
|---|---|---|---|
| Proposal Autopsy | Editorial evidence scene | Reveal missing decision, value, owner, and authority | Scope without a bounded decision is not a pilot |
| Evidence-to-Decision Spine | Network and dependency diagram | Show dependencies from question through measured result | The graph is one governed component in a decision system |
| Connected Pilot Canvas | Interactive system map | Trace each choice to downstream requirements | Every choice must support the bounded decision |
| Ninety-Day Evidence Roadmap | Timeline and phase-gate map | Separate activity from evidence-producing milestones | A pilot exists to reduce uncertainty |
| Review Board Decision Matrix | Governed comparison table | Expose hard gates and tradeoffs | A score cannot compensate for a failed hard gate |

Distinctiveness controls:

- Do not use Module 18's control-room visual language or state machine.
- Do not repeat Module 17's operating lanes.
- Do not use a generic layered architecture stack as the hero visual.
- Preserve the capstone review-board identity across the experience.

## Conversational teaching sequence

1. Ask what decision the overbuilt proposal serves.
2. Separate enterprise ambition from a bounded pilot.
3. Run the Graph Fit Test before selecting RDF.
4. Recover the Modules 1 through 18 artifacts.
5. Define competency questions and proof queries.
6. Define identities, concepts, relationships, validation, inference, and provenance.
7. Choose what remains virtual, indexed, or materialized.
8. Connect runtime context and the Module 18 Agent Action Contract.
9. Define owners, security controls, tests, measures, and stop conditions.
10. Assemble the Pilot Canvas.
11. Defend the recommendation before the Review Board.
12. Export the professional decision briefing.

## Professional work product

The One Water Knowledge Spine Pilot Canvas includes:

- operational question, user, decision owner, and permitted action;
- baseline, consequence, target, and Graph Fit result;
- competency questions, identities, terms, concepts, and relationships;
- sources, documents, mappings, federation choices, and materialization exceptions;
- proof queries, validation shapes, inference boundaries, and provenance;
- evidence freshness, runtime context, and abstention rules;
- Module 18 control mapping, access controls, and cybersecurity review path;
- owners, tests, ninety-day roadmap, success measures, and stop criteria;
- explicit out-of-scope items.

The Decision Briefing contains:

1. Executive recommendation
2. Operational question and baseline
3. Why a graph is or is not justified
4. Minimum viable semantic design
5. Data-in-place and evidence strategy
6. Authority, security, and action boundaries
7. Ninety-day evidence plan
8. Cost and value assumptions
9. Risks and stop conditions
10. Requested owner decision

The export must be human-readable, accessible, versioned, assumption-labeled, source-aware, and clear that design approval is not release authorization.

## Assessment architecture

| Assessment | Cognitive job | Pass condition |
|---|---|---|
| Proposal decision | Judgment | Identify missing question, baseline, owner, and authority |
| Graph Fit Test | Diagnosis | Select RDF only when relationships justify it and a simpler solution is inadequate |
| Prerequisite artifact map | Relationship mapping | Place each fieldbook artifact in its correct role |
| Hidden pilot failure | Evidence and control diagnosis | Trigger revise or stop for stale, ambiguous, unauthorized, or unverifiable conditions |
| Complete Pilot Canvas | Synthesis | Satisfy all required sections and hard gates |
| Review Board defense | Defense and transfer | Answer five reviewer roles with traceable evidence and visible uncertainty |

Hard gates are a bounded question, passed Graph Fit Test, baseline and target, evidence strategy, authority boundary, cybersecurity review path, accepted Module 18 handoff, accountable owner, acceptance tests, and stop conditions. A high score cannot override a failed hard gate.

## Module 18 handoff

The incoming Agent Action Contract must score at least 16 of 20. Every control maps to an architecture component, owner, acceptance test, failure response, and audit evidence.

Required tests cover allowed, denied, stale, ambiguous, timeout, duplicate, failed-execution, failed-verification, and corrected-record paths.

The capstone does not grant credentials, approve production access, authorize operational control, or publish a graph.

## Evidence plan and boundaries

- Standards claims use authoritative W3C evidence.
- Cybersecurity and industrial-control claims use authoritative sources in the course register.
- Knowledge Spine is identified as a course architecture term.
- Vendor examples are examples, not requirements.
- Scenario data is labeled fictional or illustrative.
- Architecture recommendations state assumptions and alternatives.
- Grounding is never described as a guarantee of correctness or safety.
- Qualified humans retain security, factual, credential, practitioner, and release review.
