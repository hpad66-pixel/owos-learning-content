# Module 07 Design Brief: Ontology Engineering in Plain Language

Status: approved for production under standing owner authorization

## Learning decision

The learner must turn a bounded utility question into a reviewed ontology slice without attempting
to model the entire enterprise.

## Experience architecture

This is a facilitated modeling workshop. The room begins with disagreement about "active customer."
Competency questions become concept cards, relationship decisions, explicit exclusions, test cases,
and a versioned release route.

## Visual Arsenal selection

| Idea | Shape | Visual | Conclusion |
| --- | --- | --- | --- |
| Disagreement hides several meanings | workshop scene | Definition conflict board | Start with the decision, not the loudest definition |
| Questions drive model scope | funnel | Question-to-concept funnel | Model only what the approved questions require |
| Included and excluded meanings | boundary canvas | Ontology scope canvas | Exclusions are design decisions |
| Models require lifecycle control | cycle | Review and release loop | An ontology is maintained like code |

## Signature mechanism

The Bounded Ontology Workshop presents six modeling decisions for active customer exposure. The
learner includes, excludes, or escalates each candidate and receives consequence-based feedback.

## Work product

The Ontology Decision Record captures competency questions, included concepts, relationships,
definitions, exclusions, reuse decisions, test cases, owner, version, and change route.

## Evidence boundary

Formal ontology is valuable where shared meaning and reusable relationships serve the use case. It
is not a universal requirement for every application or agent. Reuse requires fit analysis.
