# Module 20 Design Brief

## Module identity

- Course: Meaning Before Models
- Module: 20 of 20
- Title: One Water Knowledge Spine Lab: From Utility Question to Governed Action
- Format: Full-screen HTML applied simulation laboratory
- Estimated learning time: 90 to 150 minutes
- Design state: Ready for owner review
- Implementation state: Not started
- Publication state: Not approved

## Central learning job

The learner sees, operates, breaks, repairs, and adapts the complete Knowledge Spine pattern. The experience removes the last layer of abstraction by showing how one utility question becomes explicit relationships, governed evidence, runtime context, a controlled recommendation, an authorized simulated action, verification, and audit.

Central question:

> How does a real utility question become a governed, graph-grounded application?

Outcome:

> Build, test, break, repair, and adapt one complete question-to-action Knowledge Spine pattern.

## Relationship to Modules 18 and 19

Module 18 teaches that grounded evidence does not create permission to act.

Module 19 asks whether the bounded pilot is worth funding.

Module 20 rehearses the approved design and proves whether the learner can make the whole chain work.

The progression is:

```text
Module 18: control the action
Module 19: design and defend the pilot
Module 20: run, break, repair, and adapt the system
```

> When Overflow Event 21 occurs, which upstream assets and current evidence should a wastewater supervisor review before approving one draft inspection work order?

## Signature mechanism

### One Water Knowledge Spine Live Lab

This is a persistent full-screen workspace with five synchronized regions:

1. Scenario and step rail
2. Live graph and traversal stage
3. Evidence, validation, and context inspector
4. Action, verification, and audit console
5. Instructor explanation and learner decision panel

A choice in one region visibly changes the others. For example, accepting a weak identity match changes the graph path, evidence package, query result, validation state, and action eligibility.

The learner can:

- build;
- run;
- pause;
- inspect;
- introduce a failure;
- repair;
- replay;
- compare;
- reset;
- switch scenario;
- adapt the pattern;
- export a portable configuration.

## Instructional sequence

### Step 1: Choose one operational question

The learner selects wastewater, water, stormwater, or guided custom mode. The interface refuses broad goals such as "improve all operations with AI."

### Step 2: Identify the things

The learner identifies assets, events, observations, documents, people, policies, work, approvals, and evidence records.

### Step 3: Write explicit relationships

The learner creates subject-predicate-object statements. The live graph grows as valid triples are accepted.

### Step 4: Reconcile identity

The learner resolves LS-7 across SCADA, GIS, CMMS, and incident-report identifiers. A deliberate false match shows the downstream blast radius.

### Step 5: Define shared meaning

The learner assigns structure, taxonomy, ontology, semantic mapping, and runtime context to their correct jobs.

### Step 6: Connect data and documents

The learner chooses query-in-place, virtual mapping, indexing, caching, or materialization for each source and sees freshness, availability, security, and cost consequences.

### Step 7: Ask the graph

The learner converts the operational question into a readable SPARQL pattern. Animated traversal highlights each matched relationship and evidence source.

### Step 8: Validate the evidence

SHACL checks reveal missing asset identities, dates, units, inspector roles, citations, and freshness. The learner repairs a malformed record.

### Step 9: Control inference

The learner separates asserted fact, permitted inference, unsupported assumption, and prohibited operational conclusion.

### Step 10: Assemble runtime context

The learner assembles instructions, intent, entities, evidence, definitions, policy, permissions, time, workflow state, tools, and output constraints.

### Step 11: Generate a grounded recommendation

The simulated agent returns a relationship path, cited evidence, freshness, uncertainty, permitted next step, and prohibited conclusions.

### Step 12: Separate knowledge from authority

The learner applies the Agent Action Contract. Correct evidence can still produce ASK, REFRESH, CLARIFY, or STOP rather than ACT.

### Step 13: Execute safely

After simulated approval, the learner tests idempotency, timeout, duplicate, denied, failed-execution, and uncertain-result paths.

### Step 14: Verify and audit

The learner verifies the simulated draft work order and inspects the complete evidence-to-action audit trace.

### Step 15: Adapt the pattern

The learner switches utility domains or enters a custom use case and reproduces the governed sequence.

## Visual Arsenal selection

| Visual | Class | Teaching job |
|---|---|---|
| Living Utility Graph | Executable node-link graph | Show triples becoming a traversable evidence structure |
| Query Path Illuminator | Animated path and code synchronization | Connect readable SPARQL patterns to graph traversal |
| Meaning and Evidence Workbench | Multi-layer inspection view | Separate identity, semantics, source, validation, inference, and freshness |
| Context Assembly Chamber | Packet-composition visualization | Show exactly what enters runtime context and what happens when an element is removed |
| Graph-to-Action Flight Trace | Causal event timeline | Preserve permission, execution, verification, retry, and audit sequence |
| Scenario Transfer Map | Comparative utility map | Show which parts remain governed and which parts change across water, wastewater, stormwater, and custom cases |

These are six visual systems serving different cognitive jobs. They must not be reduced to decorative cards.

## Responsive and accessibility architecture

Desktop uses the synchronized five-region laboratory.

iPad uses a two-pane workspace with a persistent step rail and switchable inspectors.

iPhone uses a vertical guided sequence. Each step shows:

1. instructor explanation;
2. complete fit-to-screen visual overview;
3. learner decision;
4. result and debrief;
5. optional full-screen detail viewer.

Requirements:

- no default horizontal scrolling;
- no miniaturized desktop canvas on mobile;
- mobile-specific graph and trace compositions;
- structured textual equivalent for every graph state;
- keyboard and touch operation;
- zoom, pan, reset, close, and focus return;
- reduced-motion equivalence;
- readable and operable at 200 and 400 percent zoom;
- persistent state announced accessibly;
- errors identified by text, not color alone.

## Evidence boundaries

- W3C standards claims use authoritative sources.
- Utility facts and tool behavior are clearly simulated.
- The laboratory does not connect to a production graph, CMMS, SCADA, GIS, or document system.
- Query success is not truth.
- Validation success is not truth.
- Inference is not judgment.
- Grounding is not authorization.
- Simulated execution is not operational execution.
- Exported configuration is not production code or release approval.
- Custom use cases require factual, practitioner, cybersecurity, privacy, accessibility, and authority review before real use.
