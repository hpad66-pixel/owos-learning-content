01
Control-room opening

The answer is right. The action is still blocked.

At 2:14 a.m., a graph-grounded assistant identifies Lift Station LS-7 as a likely upstream contributor to Overflow 21. The path is explicit, the identifiers resolve, and the cited maintenance history supports inspection. The assistant proposes creating a Priority 1 corrective work order.

Now the control room interrupts. The latest inspection is outside the approved freshness window. The signed-in operator may draft work but may not set Priority 1. A maintenance supervisor must approve that priority because it commits staff and may displace other emergency work. The answer may be useful and still be unauthorized.

This module is about that boundary. Knowledge supports a proposal. Policy and authority control whether software may change external state.

The evidence path is well grounded, but the operator lacks Priority 1 authority. What may the agent do?

Decision check

Choose the strongest answer, then check it. The feedback explains the boundary.

02
Foundation distinction

A safe action needs two independent keys

The first key asks whether the proposal is fit to consider. Did the agent resolve the right lift station? Are the relationships and source records traceable? Is required evidence present, current, within authority, and free of unresolved conflicts? Did declared validation checks pass?

The second key asks whether this actor may perform this action now. Who is authenticated? Which policy applies? What authority has been delegated to that role? Is the requested tool and parameter range allowed? Is human approval mandatory? What must make the system ask, refresh, clarify, or stop?

Do not collapse these keys into one confidence score. A high-confidence answer can be outside authority. An authorized operator can still lack adequate evidence. Both failures must remain visible.

Match each action state to its operating meaning.

Relationship matching

Plain-language rule

Do not ask only, 'Is the answer correct?' Ask, 'Is the evidence fit, is the action permitted, and can the outcome be verified and recorded?'

03
Graph-to-action worked example

Follow six triples all the way to a controlled result

Now make the grounding visible. The graph asserts that LS-7 contributes to Overflow-21, Inspection-443 inspected LS-7, and the inspection was recorded on June 1. A policy statement sets a twenty-four-hour freshness limit. Two authority statements say Operator-77 may create a draft work order but may not assign Priority 1.

Those statements do not collapse into one answer. Graph retrieval resolves the asset and evidence. Declared validation detects that the inspection is stale. The authorization service permits only a draft. Policy requires the named supervisor to approve Priority 1. After current evidence and approval exist, the tool receives one bounded request. The system then reads the Computerized Maintenance Management System to verify the resulting record and binds that result to an audit receipt.

The dates, priority names, roles, and approval thresholds in this example are illustrative utility policy assumptions, not universal industry rules. Every utility must replace them with its own approved classifications, delegation rules, emergency procedures, regulatory duties, and operational-technology boundaries.

The testable conclusion

If another team cannot identify which graph statement, validation result, policy decision, approval receipt, tool request, verification record, and owner produced the outcome, the application is not yet governed.

04
Governed action lifecycle

The proposal moves through states, not one leap

A proposal begins as a recommendation, not an action. Validation checks its required evidence and data contract. Authorization compares the authenticated role, policy, action, asset, time, and parameter limits. Approval records a human decision when policy requires one.

Only then may the tool execute. Verification reads the resulting external state instead of trusting a success message alone. Recording binds the proposal, evidence receipt, policy decision, approval, tool request, tool response, verification, time, and accountable owners.

ASK, REFRESH, CLARIFY, and STOP are not system failures. They are controlled outcomes that prevent uncertainty or missing authority from silently becoming action.

05
Executable boundary

The action travels inside a contract

A tool call should never be an unbounded sentence such as 'fix the overflow.' The action envelope names the exact tool, allowable parameters, target identity, preconditions, authenticated actor, policy decision, approval receipt, time window, and expected postcondition.

The envelope also names what the agent may not do. For this case, the system may draft a work order after evidence refresh. It may not assign Priority 1, dispatch a crew, change a setpoint, open a valve, or represent that the overflow cause is proven.

Resource Description Framework graph statements can connect the proposal to the asset, event, evidence, policy reference, approver, and receipt. The authorization service and operational tool still enforce permission and execution.

06
Practitioner recovery

A timeout is not permission to repeat a side effect

Suppose the work-order tool times out after the request leaves the agent. The agent does not know whether the external system created the order. Repeating the same call may create a duplicate Priority 1 task.

An idempotency key gives one intended action a stable request identity. Before retrying, the agent or orchestration layer checks the tool receipt or reconciles external state using that key. If the result remains unknown, it stops and escalates. A retry policy must distinguish safe read operations, safe repeatable writes, duplicate-protected writes, and writes that require human reconciliation.

Verification is separate from execution. A success response says the tool accepted something. Verification confirms the intended postcondition, such as one draft work order linked to LS-7 with the approved priority and evidence receipt.

07
Accountability rehearsal

The audit trail must answer a future investigator

Months later, an investigator should not have to infer why the action occurred from a chat transcript. The record should answer what was proposed, which evidence was used, what was stale or disputed, which policy version applied, who or what was authenticated, who approved, which tool call ran, whether it was retried, what external state resulted, and who owns correction.

Provenance describes where information and activities came from. It does not make the source authoritative for every purpose, and it does not assign legal or operational accountability automatically. Those boundaries belong in policy, role design, contracts, and review.

Professional application

Write the boundary before the agent receives the tool

Write the Agent Action Contract for the wastewater work-order scenario. Begin with the smallest useful action. A strong first boundary may permit a draft work order after current evidence is retrieved while reserving priority, dispatch, operating changes, and closure for named humans.

Use test cases before deployment: allowed, denied, stale, ambiguous identity, conflicting evidence, approval required, tool unavailable, timeout with unknown result, duplicate request, failed verification, and correction after a wrong action. Another team should be able to test the contract without guessing what you meant.

Questions people actually ask

If the graph answer is correct, why not let the agent act?

Correctness addresses the knowledge question. Action also requires authenticated authority, policy eligibility, acceptable risk, tool scope, approval when required, safe execution, verification, and accountability.

Does RDF provide authorization?

No. RDF can represent relationships among actors, roles, policies, assets, evidence, and actions. An authorization service and operational controls must enforce permission.

Does every agent action require a human?

Not necessarily. Leaders can delegate low-risk, reversible, well-tested actions within explicit limits. Higher-impact, irreversible, ambiguous, stale, or exceptional cases can require human approval.

What should happen when evidence is stale?

The contract should name the freshness threshold and response. The system may refresh, ask for current evidence, downgrade to a draft, or stop. It should not silently treat stale evidence as current.

What is idempotency in plain English?

It means the same intended request can be recognized as the same request, so a retry does not accidentally create a second work order or repeat another side effect.

What if the tool times out after acting?

Treat the outcome as unknown. Check a receipt or reconcile external state using the idempotency key. If the result cannot be proven, stop and escalate instead of repeating blindly.

Is a tool success response enough?

No. Verify the intended postcondition in the authoritative system and record the verification result.

Who is accountable when an agent acts?

The organization must name owners for policy, delegated authority, tool integration, evidence, monitoring, incident response, and correction. The model itself is not an accountable utility officer.

Evidence boundary

RDF, SHACL, and provenance can support grounding, declared validation, and traceability. They do not by themselves provide authentication, authorization, orchestration, cybersecurity, safe tool execution, or human accountability.

Module Glossary

agentic application

Software that uses a model or other decision logic to plan or select steps and invoke tools within an operating boundary.

grounding

Connecting an answer or proposal to identified evidence, relationships, sources, and applicable meaning.

authorization

The decision that an authenticated actor may perform a specific action on a specific target under current policy and conditions.

delegated authority

A bounded set of actions an accountable owner permits a role or system to perform without a new approval each time.

tool contract

The allowed operation, input schema, parameter limits, preconditions, outputs, errors, and postconditions for an external tool.

idempotency key

A stable identifier for one intended request that helps a receiving system detect and prevent duplicate side effects.

external state

The current condition of a system outside the model or agent, such as whether a work order already exists.

postcondition

The state that must be true after an action succeeds, verified in an authoritative system.

audit receipt

A linked record of proposal, evidence, policy, approval, tool execution, verification, time, and accountable ownership.

stop state

A controlled outcome that prevents an unsafe, prohibited, ambiguous, stale, or unverifiable action from proceeding.
