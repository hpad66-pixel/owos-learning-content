Inspection language

SHACL asks whether a graph conforms to explicit shapes

SHACL stands for Shapes Constraint Language. A data graph contains the statements you want to inspect. A shapes graph contains the expectations. A focus node is one node being checked.

A shape can identify a path and apply a constraint. For Pump P-104, sh:minCount 1 on assetIdentifier says at least one value is required. sh:datatype xsd:date on installationDate says the value must have that datatype.

The output is a validation report. A validation result points back to the focus node and source constraint component. That trace is why SHACL is more useful than a red banner saying simply “bad data.”

Important boundary: SHACL validates against the selected shapes. It does not prove that the underlying real-world fact is true. A correctly typed installation date can still be the wrong date.

Remediation floor

Severity supports routing, not automatic risk authority

SHACL defines severity values including sh:Violation, sh:Warning, and sh:Info. Those labels can organize validation results. They do not know your emergency plan, permit condition, or customer impact. The utility must define what each result means for each workflow.

A missing identifier might block an asset handoff because records cannot be reconciled. An unexpected status value might require a mapping correction. An old descriptive label might be informational. The same technical finding can have a different workflow consequence when the operational purpose changes.

Compare, then route

First separate ontology reasoning from SHACL validation. Then follow one hidden defect into an agentic failure. Finally assign each finding to a practical response. The goal is controlled remediation, not collecting more red icons.

Inspection FAQ

Questions about SHACL in utility work

Does SHACL clean the data automatically?

No. SHACL produces validation results. A separate governed process decides whether to correct a source, repair a mapping, accept an exception, or stop a handoff. Automatic repair can create new errors if authority and intent are unclear.

Does a conforming graph prove the real-world facts are correct?

No. It proves that validation produced no relevant results against the selected shapes and data. A value can have the right datatype and still describe the wrong pump. Source verification remains necessary.

Why not express every requirement in one giant shape?

Different workflows need different evidence. A public map, a maintenance handoff, and an emergency operating brief have different requirements. Smaller versioned shape sets are easier to own, test, explain, and change.

Are SHACL severities the same as utility risk levels?

No. SHACL severities label validation results. Your utility must map them to workflow consequences using operational risk, regulation, safety, and service impact. That mapping needs named ownership.

Can SHACL validate relationships, not just fields?

Yes. Property paths and shape constraints can test connected graph structures. For example, an outfall could be required to connect to a receiving water resource or a sample to a method and unit.

Where should validation run?

Useful locations include ingestion, mapping tests, graph publication, query-time handoffs, and pre-action agent workflows. Choose the location that catches the defect before it becomes expensive while keeping latency and ownership practical.

Evidence boundary

The Pump P-104 findings and routing choices are instructional. SHACL defines validation constructs and reports, but each utility must define authoritative sources, workflow consequences, severity policy, exception handling, and remediation ownership. No example here authorizes an operational action.
