# Curriculum Package

## Instructional thesis

Meaning becomes teachable when learners can point to one relationship, say it aloud, and test what
follows from it. The course therefore moves in a deliberate sequence:

```text
name the relationship
-> identify the things
-> connect the statements
-> share the vocabulary
-> ask a graph pattern
-> infer under explicit rules
-> validate declared constraints
-> attach source, authority, and time
-> connect meaning to data and documents
-> assemble task-specific context
-> ground an application
-> govern an action
```

## Signature utility scenario

Pump P-104 anchors the course. It appears in SCADA, GIS, CMMS, drawings, work orders, observations,
procedures, a pressure zone, customer impact, and staff language. Its graph grows as the learner's
capability grows.

The scenario is fictional. Production values must be reviewed for plausibility before release.

## Recurring misconception sequence

| Misconception | Course correction |
| --- | --- |
| “The records have the same label, so they are the same thing.” | Identity requires governed evidence and stewardship. |
| “A triple is just three columns.” | A triple makes a directed, named relationship using reusable identifiers. |
| “The graph picture is the knowledge.” | The machine-readable statements, semantics, and evidence are the knowledge representation. |
| “RDFS, OWL, and SHACL are interchangeable.” | Description, inference, and validation are different jobs. |
| “No record means false.” | Under open-world reasoning, no record usually means unknown. |
| “Passed SHACL means true.” | It means the graph met the declared structural constraints. |
| “An inferred statement came from the language model.” | Logical entailment and generated language are different processes. |
| “RAG changes every time.” | Variability depends on retrieval, ranking, prompts, decoding, tools, and source change. |
| “A graph is deterministic.” | Repeatability belongs to the configured pipeline, not the technology label. |
| “An agent can act because it knows.” | Evidence, permission, validation, and human approval remain separate controls. |
| “A data model, ontology, semantic layer, and context are the same thing.” | Structure, shared meaning, enterprise connection, and runtime packaging are different jobs. |
| “The ontology exists, so the system uses it.” | Meaning must be instantiated, mapped, queryable, governed, and connected to runtime use. |
| “Data in place means no copies exist anywhere.” | Indexes, caches, extracts, results, and hot paths may still be governed materializations. |
| “Embeddings turn documents into approved knowledge.” | Similarity, extraction, graph assertion, review, and approval remain separate stages. |

## Utility example domains

- Water: sources, treatment, pumps, tanks, pressure zones, valves, mains, meters, customers, samples,
  advisories, and work.
- Wastewater: laterals, collection segments, lift stations, overflows, samples, treatment processes,
  discharge points, biosolids, permits, and corrective actions.
- Stormwater: inlets, pipes, catchments, outfalls, inspections, rainfall, debris, receiving waters,
  permits, and maintenance.
- Enterprise: people, roles, qualifications, procedures, policies, contracts, projects, decisions,
  risks, vendors, and accountable organizations.
- Individual knowledge: observations, local names, troubleshooting steps, cautions, hypotheses, and
  expert statements with review status.

## Simulation rules

Every simulation must expose:

1. The exact input records.
2. The generated or selected triples.
3. Source identifiers and canonical identifiers.
4. Which statements are asserted, inferred, validated, approved, or generated.
5. The query, rule, shape, or tool call that produced the next state.
6. What is fixed, what may vary, and what is unknown.
7. The person or role accountable for review.

## Visual progression

The visual language grows with the learner:

- cards for one relationship;
- lanes for source-system identity;
- node-link views for paths;
- taxonomy trees for shared vocabulary;
- query overlays for SPARQL;
- proof traces for inference;
- contract and report views for SHACL;
- timelines and authority badges for provenance;
- a five-layer comparison for data model, taxonomy, ontology, semantic layer, and AI context;
- mapping bridges from source fields to graph meaning;
- virtualize-or-materialize decision trees;
- structured-unstructured evidence bridges;
- runtime context packet assembly;
- pipeline comparisons for BI and RAG;
- state machines for agentic action;
- an architecture canvas for the capstone.

No decorative stack diagram should substitute for explaining the job of each standard.

## Instructional views

Foundation, Practitioner, and Leader views use the same scenario and claims. Learners may change
view at any point without losing progress. The course remembers the selected view but never hides a
safety boundary.

## Capstone

The Utility Semantic Backbone Pilot Canvas contains:

- one bounded operational question;
- users and decision owner;
- current answer path and pain;
- entities and canonical identities;
- initial triple set;
- vocabulary owner;
- three SPARQL competency questions;
- one SHACL contract;
- optional inference with explicit justification;
- source, authority, time, and version requirements;
- semantic mappings and change controls;
- structured and unstructured evidence plan;
- virtual, indexed, cached, or materialized access decisions;
- artificial intelligence context contract;
- access, cybersecurity, and human-approval boundaries;
- integration with BI, RAG, or an agent;
- baseline and target measures;
- stop conditions and next review.

## Proposed success measures

Choose measures tied to the pilot question:

- time to assemble evidence;
- duplicate or conflicting asset identities;
- manual joins or handoffs;
- unresolved data-quality violations;
- percentage of answers with traceable evidence paths;
- time to determine affected customers or assets;
- false escalation and missed escalation rates;
- stale or superseded procedure use;
- analyst rework;
- approved agent actions, denied actions, and human overrides.

## Review gates

1. Maintain approval evidence for the twenty-module curriculum and lesson contracts.
2. Approve the Module 01 golden-lesson treatment.
3. Validate the fictional utility scenario with operations, engineering, data, and cybersecurity
   reviewers.
4. Pilot the Foundation view with nontechnical staff.
5. Pilot the Practitioner and Leader views.
6. Lock assessment scoring and capstone rubric.
7. Complete accessibility, citation, licensing, graph, and release checks.
