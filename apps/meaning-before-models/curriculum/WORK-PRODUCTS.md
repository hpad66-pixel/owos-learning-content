## Capstone rubric

| Criterion | Developing | Ready |
| --- | --- | --- |
| Operational question | broad technology goal | one bounded question tied to a decision |
| Identity | labels only | canonical and source identifiers with conflict ownership |
| Relationships | disconnected list | useful, directed triples that answer competency questions |
| Layer distinction | data model, ontology, semantic layer, and context blended | each layer has a defined job and handoff |
| Shared meaning | undefined terms | definitions, classes or properties, and named owner |
| Query | generic desire | three testable graph-pattern questions |
| Reasoning | implied intelligence | explicit optional axioms and inference boundaries |
| Validation | “good data” | one readable SHACL contract and violation workflow |
| Provenance and time | source system named | source, authority, effective time, version, and supersession |
| Data access | copying or virtualization assumed | access pattern chosen from freshness, latency, cost, security, and availability |
| Runtime context | generic prompt | context contract includes evidence, policy, time, permissions, state, and limits |
| Agent control | autonomous aspiration | allowed tools, access, approvals, stops, and writeback |
| Value | abstract strategic benefit | baseline, target, measurement owner, and review date |
| Fit | RDF assumed | reasoned RDF-fit decision and simpler alternatives considered |

## Submission rule

The capstone is complete only when another utility staff member can read the canvas and answer:

1. What question are we trying to answer?
2. Which things and relationships must be represented?
3. Where did each important statement come from?
4. What may the system infer or validate?
5. What may an agent do, and who must approve it?
6. How will we know the pilot helped?
