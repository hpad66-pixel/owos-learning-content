# Module 6 Design Brief: Guardrails Are Part of the Design

Status: curriculum build

## Learning job

An agent asks for permission to modify a customer record after reading untrusted content. The learner must configure identity, permissions, checks, retry limits, approval, and escalation before the action can proceed.

## Outcomes

The learner can distinguish instructions from guardrails, apply least functionality and least privilege, identify excessive agency, set human approval points, and design an observable response to failure.

## Experience design

| Element | Design |
| --- | --- |
| Narrative | Permission console and failure laboratory |
| Mental model | Useful independence inside layered boundaries |
| Visuals | Permission ladder, defense layers, failure tree, retry gauge, identity bridge, audit timeline |
| Interaction 1 | Configure read, retrieve, recommend, draft, write, and execute permissions |
| Interaction 2 | Inject stale data, prompt injection, tool failure, excessive retries, and missing owner |
| Quiz mix | Scenario choice, multi-select, matching |
| Work product | Guardrail and Human-Authority Plan |
| Capstone | Define allowed actions, prohibited actions, approvals, limits, and escalation |
| Graph | Risks connect to controls, identities, tools, actions, owners, and evidence |
| Mobile | Console becomes a guided permission stepper |

## Operational-technology boundary

The lesson separates information-technology examples from operational technology that monitors or controls physical processes. No simulation authorizes live operational control.

## Completion evidence

Permission configuration, three failure recoveries, authority map, knowledge check, and saved guardrail plan.
