1 | Protect the decision path

Security controls data so utility decisions remain trustworthy

Integrity asks whether the information and configuration are what they claim to be. Security manages threats to confidentiality, integrity, and availability. Resilience asks whether Riverbend can maintain or safely restore the public-service function.

These jobs overlap, but they are not interchangeable. Least privilege may limit who can change a setpoint. A change record proves which approved change was intended. Integrity monitoring can detect an unexpected difference. Independent physical checks help determine actual plant state. Backup and recovery evidence shows whether Riverbend can restore a known-good configuration within the required time.

Protect the service, not only the server. In operational technology, the safe fallback may involve operators, local controls, laboratory checks, physical valves, communication plans, and emergency authority. A successful system restart is not the same as safe service recovery.
Worked control-room example

Separate four questions before acting

What is physically true?Independent analyzer, grab sample, local indication, pump state, valve position.
What changed?Account, time, command, before and after values, approved ticket, affected devices.
What can be trusted?Known-good configuration, protected log, verified identity, signed release, tested measurement.

The fourth question is what Riverbend can do safely now. The operator follows the approved fallback, confirms the chemical residual through independent measurement, isolates the questionable remote path, preserves logs, and notifies the incident roles. The system owner compares controller configuration with the approved baseline. Recovery proceeds only after the utility verifies the source of truth, tests the restored state, and records authority to return to service.

2 | See the protected path

One decision crosses several trust boundaries

Read this path from physical process to operator action. Each boundary needs a different kind of proof. Sensor identity and calibration support the measurement. Network and account evidence support the transfer and change. Configuration and deployment records support the controller. The operator still needs authority and a safe fallback.

Physical processActual water and chemical condition
MeasurementSensor identity, calibration, timestamp
ControlLogic, setpoint, account, configuration
DisplayTransfer, historian, freshness, alarm
DecisionOperator authority, action, fallback

A failure at one boundary can make later screens look normal while the underlying evidence is untrusted.

Trust is a chain of physical, technical, and human controls. Availability at the final screen does not prove integrity along the path.

Select each injected failure. The console shows how the same control path behaves when integrity, availability, or recovery evidence changes. Read every stage. The right response depends on what is known, what is uncertain, the service consequence, and the approved safe-state procedure. Compare which green controls still help and which red failure prevents Riverbend from trusting or restoring the service.

Follow the red stages to the service decision. Green stages help containment but do not erase failed controls.

Resilience requires tested response and recovery across the decision path, not a collection of disconnected technical controls.

Debrief. The three failures require different actions. An integrity event questions the truth of the state. An availability event may remove visibility while local control continues. A recovery gap questions whether Riverbend can restore a known-good state in time. The incident record should preserve those distinctions.

4 | Layer the evidence

Prevent, detect, respond, recover, learn

Read the stack from prevention to learning. No single layer is expected to be perfect. Defense comes from independent and tested layers that leave evidence. If prevention fails, detection and safe response should still protect service. Recovery should restore a verified state, and learning should change controls rather than merely close the incident.

PreventIdentity, least privilege, approved change, segmentation
DetectLogs, integrity checks, anomaly review, physical comparison
RespondAuthority, containment, safe state, communication
RecoverKnown-good baseline, tested restore, validation
LearnCause, affected decisions, retest, control update

Each layer has an operating control and an evidence record. Missing evidence should remain visible.

A resilient utility can explain how it prevents, detects, contains, restores, and learns while maintaining safe service.

Incident judgment

Select the evidence needed before return to service

Select every item that supports a return-to-service decision. Focus on verified physical state, authorized configuration, controlled access, tested operation, unresolved limitations, and accountable approval. A green dashboard alone is not enough.

Control-room questions

Integrity, security, and resilience FAQ

Is cybersecurity the information technology team’s job?

Information technology and operational technology teams operate many controls, but owners, operators, suppliers, executives, legal roles, emergency roles, and assurance all have decisions and evidence responsibilities. Safe service cannot be delegated to one technical team.

What is the difference between backup and recovery?

A backup is a copy. Recovery is the demonstrated ability to restore the required service and data to a verified state within agreed objectives. Riverbend needs restore tests, configuration checks, application validation, and operating acceptance.

Should every anomaly become a cyber incident?

No. Classify using the approved process and evidence. A sensor fault, process condition, integration defect, and hostile action can look similar at first. Preserve evidence and contain consequence without claiming a cause too early.

Can anomaly detection prove data integrity?

No. It can signal unusual behavior. Integrity also depends on identity, authorization, approved change, protected logs, source validation, configuration comparison, and sometimes independent physical evidence.

How often should recovery be tested?

Set frequency from consequence, change rate, dependencies, obligations, and risk. Test after material architecture, supplier, configuration, or procedure changes, not only on a calendar.

What should a small utility do first?

Identify the most consequential operational decisions, document safe states and contacts, remove shared or unnecessary access where practical, control changes, protect logs and backups, and conduct a realistic tabletop and restore test.
