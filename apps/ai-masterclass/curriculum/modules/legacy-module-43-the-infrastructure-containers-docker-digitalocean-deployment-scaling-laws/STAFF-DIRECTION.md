# Staff Direction for M43: The Infrastructure: Containers, Docker, DigitalOcean, Deployment, Scaling Laws

## Your assignment

Teach the production infrastructure and operating disciplines behind model, language-model, and agent applications, including cloud foundations, environments, pipelines, artifacts, deployment, observability, cost, resilience, incidents, recovery, and exit.

Open with this situation: A prototype works on one laptop, then fails in production because configuration, secrets, dependencies, traffic, logs, backups, updates, and ownership were never designed.

Ask the learner to decide before teaching begins: **Design the smallest supportable architecture and operating pipeline for a bounded utility application, assign every responsibility, and define release, observation, incident, rollback, cost, support, and exit evidence.**

Use this analogy once as the front door, then return to the utility work: A pump is only one part of a pump station. Power, controls, housing, access, maintenance, alarms, and backup make it an operating system.

The learner must leave with a saved **AI deployment, operations, and release architecture record**. If the module does not produce that
record and evidence, the module is not complete.

## Non-negotiable learner outcomes

1. Explain The Infrastructure: Containers, Docker, DigitalOcean, Deployment, Scaling Laws in plain English and connect it to a real water, wastewater, stormwater, or One Water decision.
2. Distinguish development, test, production, container, compute, storage, network, identity, secret, artifact, pipeline, continuous integration, delivery, deployment, observability, drift, incident, scaling, recovery, and exit without using one term to hide several different jobs.
3. Analyze the module situation, identify missing evidence, and name the professional consequence of a weak decision.
4. Compare how the same question changes across drinking water, wastewater, stormwater, administration, engineering, finance, technology, and public leadership.
5. Evaluate sources, assumptions, limitations, permissions, and human authority using this boundary: Keep services, prices, limits, model versions, platform features, and scaling claims dated. Do not publish credentials or facility-sensitive architecture, skip security review, or represent a classroom deployment as a supported production service.
6. Create a usable AI deployment, operations, and release architecture record with evidence, roles, limits, review steps, and the next accountable action.
7. Defend the recommendation to Foundation, Practitioner, and Leader audiences while keeping disagreement and uncertainty visible.

### `M43.CE01` Machine Learning Operations pipelines and reproducibility

Teach the operating pipeline that moves data, code, model artifacts, tests, approvals, and monitoring through controlled environments. The learner must be able to reproduce a release and recover from a failed one.

- Required work product: **Machine Learning Operations pipeline and release record**
- Secondary module connections: M05, M16, M24, M40
- Learning objectives:
  - Explain Machine Learning Operations in plain English as the controlled path from model work to supported operation.
  - Map data, code, experiment, model, test, environment, release, monitoring, and rollback dependencies.
  - Distinguish version control, experiment tracking, artifact storage, continuous integration, continuous delivery, and deployment.
  - Diagnose a reproducibility failure and identify the missing version, dependency, data, or configuration evidence.
  - Create a vendor-neutral Machine Learning Operations pipeline and release record.
- Assessment evidence:
  - pipeline dependency mapping
  - reproducibility fault diagnosis
  - release strategy decision
  - completed release record
- Evidence boundary: Use synthetic or approved data. Do not represent a classroom pipeline as a supported production service or a validated predictive model.

### `M43.CE02` Large Language Model Operations and agent operations

Unify prompt, context, retrieval, tools, models, evaluations, traces, cost, incidents, and human review as one operating discipline for language-model and agent systems.

- Required work product: **language-model and agent operations record**
- Secondary module connections: M24, M26, M31, M33, M41
- Learning objectives:
  - Explain how Large Language Model Operations differs from ordinary model deployment and ordinary software operation.
  - Version prompts, system instructions, retrieval sources, tools, permissions, evaluations, and model choices as operating dependencies.
  - Inspect a trace and separate model, source, tool, permission, orchestration, and human-review failures.
  - Define operating measures for quality, groundedness, refusal, tool correctness, latency, cost, and review effort.
  - Create an agent operations record with monitoring, incident, rollback, and human-escalation rules.
- Assessment evidence:
  - trace fault classification
  - metric and threshold design
  - incident response scenario
  - completed operations record
- Evidence boundary: A trace shows what the system recorded. It does not prove completeness, correctness, legal sufficiency, or professional judgment.

### `M43.CE03` Cloud foundations and managed AI platforms

Teach a vendor-neutral cloud foundation before a learner enters an Azure, Amazon Web Services, Google Cloud, or other platform lab. Every managed service still has identity, data, logging, cost, support, and exit responsibilities.

- Required work product: **cloud AI responsibility and exit map**
- Secondary module connections: M25, M26, M27, M42, M63
- Learning objectives:
  - Explain cloud region, network, compute, storage, identity, secret, log, managed model endpoint, and service responsibility in plain English.
  - Map data and request flow across a minimum supportable hosted artificial intelligence application.
  - Compare managed, self-hosted, local, and hybrid patterns for capability, control, privacy, cost, support, and exit.
  - Identify identity, permission, secret, network, logging, backup, cost, resilience, and vendor-dependency requirements.
  - Create a vendor-neutral cloud AI responsibility and exit map.
- Assessment evidence:
  - cloud-component matching
  - responsibility classification
  - hosting tradeoff decision
  - completed responsibility map
- Evidence boundary: Named platforms are dated examples. A managed service does not remove the utility's responsibility for data, access, evaluation, contract, cost, records, or accountable use.
