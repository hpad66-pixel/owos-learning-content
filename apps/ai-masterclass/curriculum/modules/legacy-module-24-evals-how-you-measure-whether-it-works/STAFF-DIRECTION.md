# Staff Direction for M24: Evals: How You Measure Whether It Works

## Your assignment

Teach evaluation and observability as a continuing evidence process that tests answer and task quality, source coverage, tool correctness, trajectory, policy behavior, refusal, recovery, drift, latency, cost, and human-review effort.

Open with this situation: A source-grounded assistant answers common questions well but fails on outdated procedures, conflicting documents, and questions outside its permission boundary.

Ask the learner to decide before teaching begins: **Define the test set, signals, metrics, thresholds, reviewers, incident response, regression checks, correction action, and stop rule for a utility artificial intelligence or agent system.**

Use this analogy once as the front door, then return to the utility work: A laboratory does not trust one clean sample. It uses controls, known cases, repeats, limits, and corrective action. AI evaluation needs the same discipline.

The learner must leave with a saved **agent evaluation, observability, and continuing-assurance plan**. If the module does not produce that
record and evidence, the module is not complete.

## Non-negotiable learner outcomes

1. Explain Evals: How You Measure Whether It Works in plain English and connect it to a real water, wastewater, stormwater, or One Water decision.
2. Distinguish test case, task outcome, groundedness, source coverage, tool correctness, trajectory, metric, signal, trace, threshold, benchmark, drift, incident, acceptance, and continuing assurance without using one term to hide several different jobs.
3. Analyze the module situation, identify missing evidence, and name the professional consequence of a weak decision.
4. Compare how the same question changes across drinking water, wastewater, stormwater, administration, engineering, finance, technology, and public leadership.
5. Evaluate sources, assumptions, limitations, permissions, and human authority using this boundary: A benchmark, dashboard, average score, missing alert, or one successful demonstration does not prove utility fitness, safety, fairness, compliance, or performance under changed conditions.
6. Create a usable agent evaluation, observability, and continuing-assurance plan with evidence, roles, limits, review steps, and the next accountable action.
7. Defend the recommendation to Foundation, Practitioner, and Leader audiences while keeping disagreement and uncertainty visible.

## Accepted 2026-08-11 curriculum expansions

These records are approved for curriculum-blueprint integration. Their factual claims, finished teaching, assessment implementation, and release remain gated.

### `M24.CE01` Agent-specific evaluation and continuous assurance

Extend evaluation from answer quality to the complete agent trajectory, including task result, tool use, source coverage, policy behavior, recovery, latency, cost, and human-review effort.

- Required work product: **agent evaluation and continuing-assurance plan**
- Secondary module connections: M26, M31, M41, M43, M53
- Learning objectives:
  - Define task success and failure before selecting an agent metric.
  - Evaluate answer quality, groundedness, source coverage, tool-call correctness, trajectory, refusal, recovery, latency, cost, and human effort.
  - Build a representative test set with ordinary, boundary, adversarial, stale, conflicting, and failure cases.
  - Set acceptance thresholds, stop rules, regression tests, reviewers, and correction actions.
  - Create an agent evaluation and continuing-assurance plan.
- Assessment evidence:
  - metric-to-failure matching
  - test-case classification
  - threshold and stop decision
  - completed assurance plan
- Evidence boundary: An average score or one successful demonstration does not prove fitness for a utility task, safety, fairness, compliance, or performance under changed conditions.

### `M24.CE02` Observability, drift, degradation, and incident response

Teach how a team notices that data, sources, model behavior, prompts, tools, permissions, infrastructure, cost, or human work has changed, then pauses, investigates, corrects, and records the response.

- Required work product: **AI observability and incident-response record**
- Secondary module connections: M05, M25, M26, M31, M43
- Learning objectives:
  - Explain observability as the evidence needed to understand a changing system, not as a dashboard alone.
  - Distinguish data drift, concept drift, model degradation, retrieval staleness, prompt regression, tool failure, permission change, and workflow change.
  - Select signals, logs, traces, thresholds, alerts, owners, and response times for one utility application.
  - Investigate an incident without overwriting prior evidence and decide whether to continue, restrict, roll back, or stop.
  - Create an artificial intelligence observability and incident-response record.
- Assessment evidence:
  - change-type classification
  - signal and threshold design
  - incident decision simulation
  - completed incident record
- Evidence boundary: A missing alert does not prove a system is healthy. Monitoring scope, blind spots, retention, privacy, and responsible human response must remain visible.

## Quality-control team

Reject the module when:

- the learner cannot explain the core distinctions among test case, task outcome, groundedness, source coverage, tool correctness, trajectory, metric, signal, trace, threshold, benchmark, drift, incident, acceptance, and continuing assurance;
- the opening situation disappears and the module becomes a glossary or product tour;
- the work product has no source, role, limitation, review, or next-action fields;
- a current section, proposal, subtopic, enhancement, or contributor record is omitted or moved
  without provenance;
- a visual has no teaching conclusion or an interaction has no consequence;
- assessment does not test the stated outcomes or provide feedback and retry;
- a role example changes the standard instead of the context;
- marketing makes an unsupported outcome claim;
- accessibility and phone use are left for later; or
- the evidence, learning-design, practitioner, technical, or release gate remains unresolved.
