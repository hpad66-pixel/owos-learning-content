# OWOS Course Production Activation Prompt

Version: 1.0.0

Use this prompt for a new course, continued course, retrofit, or final course audit. It is
topic-neutral and module-count-neutral. Replace bracketed values when known. Repository evidence and
approval records control when they conflict with memory.

## Where the course begins

A brand-new course begins in the conversational Codex workspace with topic sparring, research, and
course formulation. It does not begin in Author Studio and it does not begin by generating module
HTML.

Author Studio is the controlled review and editing surface used after the curriculum, course
experience architecture, and lesson contracts exist. It lets Hardeep inspect and revise structured
narrative, storyboard, visuals, interactions, assessments, sources, glossary, QA, and compiled
preview module by module. It does not decide what the course should teach.

```text
Continue the OWOS course “[COURSE TITLE OR SLUG]” as a governed, world-class written learning
experience. Apply the complete repository production system. Do not skip research, approvals,
human review, quality gates, or release controls.

Use the course AGENTS.md and continue-owos-course skill. Read the course brief, state, approvals,
syllabus, lesson contracts, Hardeep Soul, authoring standard, Course Production Contract, Course
Operating Standard, Course Design System, Course Experience Architecture, Visual Arsenal, Writing
Standard, component catalog, quiz catalog, templates, rendered galleries, this activation prompt,
and prior QA evidence. Preserve my direction in conversations/ and update durable repository memory.

Execute this governed sequence. Report the current phase and its exit evidence before moving to the
next phase:

0. Topic sparring and intake
   Begin in the Codex conversation. Help me sharpen the topic, intended learner, utility problem,
   point of view, boundaries, candidate outcomes, examples, and unanswered questions. Ingest my
   research, documents, annotations, and spoken direction without forcing a module count. Preserve
   the conversation and originals. Produce an intake brief and research plan. Do not open Author
   Studio or generate lessons yet.

1. Research and evidence
   Preserve originals and checksums. Separate sourced facts, expert interpretation, Hardeep
   positions, utility examples, teaching direction, and unresolved questions. Maintain source,
   claims, and evidence-boundary registers. Use primary sources for load-bearing claims and verify
   current information. Exit with research coverage, a source register, claims register, evidence
   boundaries, and an unresolved-question list.

2. Course formulation
   Define the learner, prerequisites, course promise, graduation capability, measurable outcomes,
   depth model, evidence boundaries, work-product progression, assessment strategy, graph plan, and
   modality. Exit with an approved Course Brief. Do not decide the number of modules by habit.

3. Syllabus and curriculum architecture
   Starting with the graduation capability, determine what the learner must understand first,
   second, third, and thereafter. Group only coherent learning jobs into modules. Define module
   outcomes, prerequisites, dependencies, transfer tasks, work products, and the final synthesis.
   Test for missing prerequisites, overloaded modules, unnecessary repetition, and a credible
   beginning-to-graduation arc. The number of modules emerges from this analysis. Exit with an
   approved syllabus, curriculum sequence, and course design matrix.

4. Experience architecture
   Create the course-specific experience brief and design matrix. Establish a distinct teaching
   voice, utility world, visual language, artifact family, interaction rhythm, and prohibited
   motifs. A common quality standard must never become a common page composition.

5. Lesson contracts
   Create one contract for every approved module before bulk production. Lock its learning job,
   prerequisite, misconception, utility decision, required claims, exclusions, transfer evidence,
   work product, and relationship to adjacent modules. Validate the complete set.

6. Golden lesson design and approval
   Select the lesson that best tests the course's hardest teaching and interaction requirements.
   Create its module design brief, Visual Arsenal selection, and storyboard. Define its narrative
   arc, opening, visuals, signature mechanism, interactions, assessment jobs, professional work
   product, FAQ, evidence boundary, accessibility treatment, and differences from adjacent lessons.
   Build, render, score, and review this one lesson. Approval establishes a capability benchmark,
   never a page template.

7. Structured module production
   Author materially built modules as structured source, not hand-edited delivery HTML. Keep
   module.yaml, storyboard.yaml, design-brief.md, visuals/visual-manifest.yaml, interactions.yaml,
   assessments.yaml, sources.yaml, glossary.yaml, qa.yaml, and real assets separately reviewable.
   Validate before deterministic compilation. The compiler renders approved teaching; it does not
   invent or flatten it. Produce in prerequisite order, normally one to three modules per batch.
   Run distinctiveness after every batch.

8. Complete written teaching
   Write conversationally for an intelligent utility professional who is new to the topic. Define
   terms, spell out acronyms, use water, wastewater, and stormwater examples, and explain what the
   learner sees, does, notices, and concludes. The written lesson must stand without video. Do not
   use em dashes, corporate filler, cryptic fragments, unsupported claims, decorative stock art, or
   repeated factory prose.

9. Visual reasoning and containment
   Build the two to five substantial visuals the ideas require, normally including at least four
   different visual classes in a full master-class module. Count only real original,
   permission-cleared, or governed executable assets. Give each visual a teaching idea, learner
   conclusion, reading guide, alternative text, mobile and reduced-motion treatment, creator,
   source, license, permission, originality, storyboard, and rendered-review state.

   Render and measure every SVG. No text may clip, overlap, escape an intended container, become
   unreadable through compression, or fail on desktop, tablet, phone, or zoom. Check padding,
   connectors, wrapping, contrast, label size, and reading order. Source inspection is not visual
   review.

10. Interactions and assessment
   Give every lesson a subject-specific signature mechanism. Simulate process, decision,
   relationship, computation, cause, or consequence when prose would ask the learner to take the
   mechanism on faith. Select quiz types from the cognitive job, distribute them beside the
   teaching, provide immediate explanatory feedback and retry, and finish with an applied
   demonstration tied to the professional work product. Do not repeat one quiz sequence.

11. Accessibility and connected learning
   Preserve semantic landmarks, keyboard operation, focus return, touch, contrast, zoom, reduced
   motion, alternative text, responsive drawers, Graph, Community, Start, bottom connected
   learning, and module-specific FAQs. Dark text on dark surfaces, empty controls, keyboard traps,
   missing focus, and horizontal overflow are release blockers.

12. Module review and Author Studio
    After a structured candidate compiles, use Author Studio when Hardeep wants controlled
    module-level inspection or revision. Review Narrative, Storyboard, Visuals, Interactions,
    Assessments, Sources, Glossary, QA, and Preview without editing delivery HTML. Approved source
    changes return through validation and compilation.

13. Deterministic QA
    Run package validation, compiler tests, lesson-contract validation, module and whole-course
    conformance, distinctiveness, structured-authoring audit, release-manifest verification,
    formatting checks, SVG containment, and rendered browser tests. Test local, packaged, and live
    desktop, tablet, and phone experiences. Verify interactions, assessments, work products,
    completion, drawers, focus return, images, console errors, overflow, motion, navigation, and
    required authentication behavior.

14. Evidence-backed scoring
    Complete a Module Quality-Control Report for every lesson and a Course Quality-Control Dossier
    for the course. Back every score with the exact package, checksum, compiler version, screenshot,
    browser run, automated check, manual review, defect, repair, commit, deployment, or live proof.
    A number cannot override blocked accuracy, practitioner, accessibility, technical, security,
    credential, or release gates. State all pending human review.

15. Course assembly and landing page
    Build the landing page only after the approved curriculum exists. Make it a course-specific
    orientation experience that explains the promise, learner route, parts, module sequence,
    prerequisites, expected work, completion state, and how to begin. Test its typography,
    hierarchy, navigation, accuracy, responsiveness, drawers, links, and accessibility. Do not use
    one generic catalog page for every course.

16. Release and proof
    Release only with authority. Commit intentional source and reproducible output, push GitHub,
    import the exact learning-content commit, run platform tests, deploy the exact production commit,
    compare custom-domain files with deployed artifacts, and rerun live browser QA. Do not say
    “published” until the custom domain is verified.

17. Durable completion package
    Store the course dossier, module scorecards, rendered evidence index, source and claims status,
    manifest, Git SHAs, deployment, live URLs, unresolved gates, correction process, and lifecycle
    owner under apps/<course>/qa/. Update STATE.md and APPROVALS.md and give Hardeep direct links.

Do not stop between implementation, testing, Git publication, deployment, and live verification
when end-to-end production is authorized. Stop only for an unsupplied factual boundary, curriculum
decision, benchmark approval, credential claim, graph publication, destructive action, or release
authority.

Run parameters:
- Course: [COURSE TITLE OR SLUG]
- Scope: [NEW COURSE / MODULES / RETROFIT / COMPLETE COURSE]
- Approved curriculum: [REFERENCE OR STATUS]
- Approved golden lesson: [REFERENCE OR STATUS]
- Publication authority: [DRAFT ONLY / LIVE REVIEW / FINAL RELEASE]
- Required sequencing: [IF ANY]
```

For the required course-end audit, use the same prompt with:

```text
Scope: Complete-course evidence audit, final quality-control dossier, release packaging, and live
verification. Do not create new teaching unless a documented defect requires correction.
```

Store the result at `apps/<course>/qa/course-quality-control-dossier.md` using
`core/templates/COURSE-QUALITY-CONTROL-DOSSIER.md`.
